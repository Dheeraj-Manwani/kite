# Explain it on a whiteboard

Ask "explain how a TCP handshake works" or "sketch how React renders" and Kite opens a whiteboard. It draws the idea one piece at a time in a hand-drawn style while it narrates, and the kite holds the marker. Turn it off in **Settings → Actions**.

Implementation checked on **8 October 2026**: **phase 1 is complete (9/9 items)**. Phase 0's tooling is implemented; its three-provider baseline gate remains pending. Phase 2 is next. See [the phase roadmap](whiteboard-roadmap.md#implementation-status--8-october-2026) for evidence and measurement conditions.

## Using it

- **Start:** ask Kite to explain, compare, or walk through something with a tool-capable model. No approval is needed: the board is Kite's own drawing and nothing on your PC changes.
- **Follow:** each beat is spoken (or captioned when voice is off) while its shapes, arrows, and words are drawn. Parts Kite talks about again get circled. **Settings → Actions → Whiteboard captions** can keep captions visible during speech; they also show when no voice is selected or accessibility support is active.
- **Voice commands** (hold the shortcut and say):
  - "wait", "pause" → pause. The current beat stays on the board.
  - "continue", "go ahead" → carry on (the paused beat is said again).
  - "next", "skip" → the next beat.
  - "repeat", "say that again" → the current beat again.
  - "replay", "start over" → the whole lesson from the beginning.
  - "close the board", "stop" → put the board away.
- **Ask about it:** anything else you say goes to the model, which sees every element on the board by id. It answers by adding to the same board (new beats play, then Kite waits before the rest of the original lesson) or by starting a new one.
- **Point at it:** hold the shortcut and circle or tap part of the board while asking "what's this?". Kite tells the model which elements you marked. No screenshot is taken for marks on the board.
- **Board buttons:** Pause/Resume, Next, Replay, Bigger/Smaller, Copy (PNG to the clipboard), Save (PNG to Documents › Kite Boards), and Close. Say "make it bigger" or "presentation mode" for the larger panel, and "make it smaller" to return. Drag the title bar to move it, the corner to resize it, the wheel to zoom, and the paper to pan; Fit resumes automatic framing.
- **Dev panel:** **Demo whiteboard** plays a built-in lesson ("How a kite flies") without a model.
- **Find it again:** completed or closed lessons save locally in **History → Whiteboards**. Search titles or diagram labels in the History search field and click a board to replay it. Thumbnails include the visible scene; reopening plays the saved script, including streamed and follow-up beats. Deleting its conversation deletes its saved boards. The built-in demo is not archived.

## How it works

The model plans the whole lesson in one `explain_on_whiteboard` call: a title and up to 16 beats, each with a spoken line and the elements it adds on a 1600 × 900 canvas (rectangles, ellipses, diamonds, text, arrows between elements, and lines, in eight colors with optional hatching). Kite's code sizes shapes to their labels, binds arrows edge to edge, keeps a request and its reply apart, and puts arrow labels beside the line. Drawing starts when a beat's audio starts; the next beat waits for both. [ADR 013](adr/013-whiteboard.md).

The lesson starts before the model has finished writing it. Its input streams in, and each beat is handed to the board once it is complete. Beat 1 is drawn and narrated while the model writes the rest; reaching the newest beat waits for the next. The final call adds whatever has not arrived. A lesson cut off mid-stream plays the beats that did arrive. The lesson is the whole answer: the voice turn ends on it, with no filler line. Whatever the model said before the call ends as soon as the lesson starts streaming, and narration follows it.

Lessons are repaired rather than rejected (`sanitizeLesson` in `src/shared/board.ts`):
- Elements that can't be drawn are dropped.
- Duplicate ids are renamed.
- References to ids that aren't on the board are dropped.
- Numbers are clamped.
- A shape written with `text` gets it as its label.

The model is told what was fixed.

Text uses bundled Excalifont (OFL-1.1), with shared glyph widths generated by `scripts/font-metrics.cjs` using Chromium. The default panel is 1400 × 900 on a 1080p display, capped at 90% on smaller displays. `planCamera()` frames the current beat and connected elements at a scale targeting at least 14 px text, with a 500 ms glide before drawing; reduced motion cuts to the new view. The finished-board overview can use smaller text. Coordinates still come from the model, but `repairBeats()` in `src/shared/boardLayout.ts` sizes labels, separates collisions, detours obstructed arrows while keeping their bindings, and halos text on lines. Each new beat finds space around the existing repaired picture. Rendering, model context, archives and replay use those same repaired coordinates.

## Privacy

The lesson text goes only to your configured model, as part of the conversation. The board is excluded from Kite's own screen captures. Completed or closed lessons, their scene and a small PNG thumbnail are saved locally in Kite's history database. These thumbnails are not sent to a model. Deleting conversation history deletes its boards. The Save and Copy buttons explicitly export a PNG; automatic history saving does not export files to Documents.

## Measuring

`src/shared/boardMetrics.ts` scores a board as numbers: colliding elements, labels that don't fit their shape (or had a word split), arrows and lines through shapes they don't connect, crossing arrows, free text lying on a line, and the smallest text on screen in the default panel on a 1080p display. Lesson readability is measured at each beat's camera; finished-board overview text is recorded separately. The harness and the dev panel both use it.

- **Harness:** `npm run eval:board` runs the 60 golden prompts and follow-ups through the model/tool path, applies the same scene repairs as playback, and records tokens, metrics, streaming readiness and the final call. It has no renderer, so `firstStroke` is null on fresh runs. `npm run eval:board:live` measures actual first stroke with the real overlay, using its renderer acknowledgement after font/camera readiness. `npm run eval:board:phase1` deterministically revalidates the frozen [phase 0 corpus](performance/whiteboard/phase0-baseline.json) and writes [the current repaired corpus](performance/whiteboard/latest.json) and [validation results](performance/whiteboard/phase1-replay.json). Model timings in that replay remain historical; [fresh latency samples](performance/whiteboard/phase1-live.json) are separate. `npm run eval:board:gallery` renders the [122-board gallery](performance/whiteboard/index.html).
- **Dev panel:** one line for the latest lesson, with the time from the model request to the renderer's actual first drawing frame (including the camera glide), output tokens, input/scene fixes, and lint counts. It holds numbers only, never lesson text; the same numbers are logged as `board:lesson`.

## Verification

On **8 October 2026**, all **261 unit tests** passed in a serial run; lint, type checking, native smoke tests and renderer smoke tests passed. The stored 60-prompt corpus passes zero overlaps/label overflow at all 565 beats, with minimum newly drawn text of 14 px. Live overlay first-stroke medians with voice off are 2.80 s (DeepSeek Flash) and 3.77 s (Groq GPT OSS 120B), three samples each. See [the roadmap's verification notes](whiteboard-roadmap.md#verification-and-remaining-gates) for the parallel-suite timing flake and other conditions.

- `npm test` (`tests/board-metrics.test.cjs`): each metric on small boards, nesting and containers, the 1080p text size, and per-beat counts for follow-ups.
