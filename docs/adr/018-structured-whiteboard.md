# 018 — The whiteboard model writes structure; code places it

Date: 8 October 2026. Status: implemented behind `KITE_BOARD_PHASE2=1`; release latency gate pending. Supersedes the model-coordinate contract in [ADR 013](013-whiteboard.md); its teaching, renderer, privacy and approval principles still apply.

## Problem and decision

The voice model previously wrote coordinates, dimensions, elements and narration in one large tool input. This consumed output tokens and left layout quality dependent on the model. The voice tool now takes `{ topic, focus?, level?, mode }`. A separate streaming specialist writes a version-2 `BoardScript`: title, family, nodes, edges and narrated reveal/highlight/erase beats. Local code measures text and computes the entire picture before revealing beat 1. The small tool's schema plus description is 723 characters, versus 3,723 for the previous tool at this revision.

Use compact pipe-delimited records by default. Retain coordinate-free JSON in the planner and harness for comparison. Both forms freeze nodes and edges at `ready`, before narrated beats. The incremental parser repairs invalid references and group cycles, bounds record counts, escapes literal pipes/newlines, ignores model coordinates and preserves completed beats on a truncated stream. Nothing drawn depends on a later graph delta. Closing or replacing a board aborts its planner and invalidates delayed callbacks.

The specialist has its own 4,096-token budget and `boardModel` setting. An explicit model choice wins. Automatic selection provisionally prefers DeepSeek Flash when its key is saved, otherwise the main conversation model. The selector is based on measured token use/readiness, not which development key is convenient. Groq GPT OSS uses low reasoning effort for the specialist only. The main voice model still decides whether to call the tool; that routing call is included in live latency and token measurements.

## Format evidence

[The paired comparison](../performance/whiteboard/phase2-format-decision.json) used TCP (sequence) and React (flow), both formats, on DeepSeek Flash, Groq GPT OSS 120B and Kimi K2.6. Median specialist output tokens for lines versus JSON were 274/289 on DeepSeek, 298.5/436.5 on Groq and 166.5/281 on Kimi. Corresponding graph/first-beat readiness was 1.67/1.60 seconds, 1.43/2.19 seconds and 3.39/4.67 seconds. One Kimi JSON call was rate-limited; [its separate retry](../performance/whiteboard/phase2-format-retry.json) used 374 tokens and became ready at 7.88 seconds. The failed attempt remains in the original denominator. These readiness numbers exclude voice routing and renderer startup and are not first-stroke measurements.

Lines use fewer tokens in each provider sample and generally reach a completed beat sooner. Both formats compile to clean geometry in the successful samples. [The rendered comparison gallery](../performance/whiteboard/phase2-formats/index.html) supports manual inspection. Review caught a sequence example that treated packet events as participants; the prompt now explicitly restricts sequence nodes to communicating parties. The stored generations are retained as measured, rather than regenerated silently after this prompt correction. This small comparison supports a provisional format decision; it does not establish a semantic clarity score or a statistically significant renderer-latency advantage for either format.

## Layout, stability and compatibility

Each family has its own measured layout: sequence participants/lifelines/message rows, flow decisions, nested architecture groups, tree hierarchies, cycles, layer stacks, paired comparisons, timelines and relative/grid freeform diagrams. Flow, architecture and tree use lazily loaded `elkjs` in a Node worker, with layered or `mrtree` layouts, measured labels, nested nodes and orthogonal routing. A deterministic local fallback handles layout failure. Final shared routing detours unrelated shapes and separates arrow labels. The worker is reused during active planning, releases after idle time and never runs in the overlay's frame loop.

Follow-ups reserve the complete original graph, including elements not yet revealed, and pin it. New parts find free space beside the related picture. Existing-only sequence messages get new time rows. This append-only policy avoids unavoidable relayout, so this implementation has no move-animation path; future editing that allows relayout must supply one. Randomized tests check all nine families, every revealed beat and unchanged existing geometry.

Sixty Tabler icons are sampled into point paths at build time and drawn with the ordinary pen player. No runtime SVG parser or icon package is shipped. `elkjs` is a production dependency under EPL-2.0; Tabler is a development dependency under MIT. Notices are copied under `assets/licenses/`, which Forge includes in the package. See the upstream [elkjs license and implementation](https://github.com/kieler/elkjs) and [Tabler icons](https://github.com/tabler/tabler-icons).

Archives retain the coordinate-free structure and its compiled coordinate beats. The version-1 adapter wraps existing saved lessons and replays their original coordinates without a new layout. There is no destructive archive migration. The specialist receives the request, six recent text messages and current board structure (or a label/id/binding summary for a legacy board), never screenshots or conversation image attachments. Boards and thumbnails remain local.

## Validation and release

[The phase-2 baseline](../performance/whiteboard/phase2-golden.json) recompiled 180 fresh specialist attempts (60 per provider) through the current layout: 60/60 lint-clean on DeepSeek, 60/60 on Groq and 58/60 on Kimi. Kimi's two failures were rate limits; they count against its denominator. All 178 completed lessons and 788 revealed beats have zero overlaps, label overflow, edges through unrelated shapes and unprotected text on lines. Edge crossings are reported separately and are not part of this lint-clean definition. The [178-board gallery](../performance/whiteboard/phase2/index.html) uses the real renderer. These initial lessons do not establish a full provider follow-up or semantic-accuracy score; follow-ups are covered by deterministic integration tests.

Median planner output is 234.5, 275 and 248.5 tokens respectively: 21–25% of the frozen phase-0 DeepSeek median of 1,112. This is a shared historical reference, not a provider-specific phase-0 comparison. [Live checks](../performance/whiteboard/phase2-live.json) include both model calls: median combined output is 341 tokens on DeepSeek and 498 on Groq, also below 556. The [60-element worker/layout/lint benchmark](../performance/whiteboard/phase2-layout.json) has a 29.83 ms warm median and 35.78 ms maximum; cold startup is 169.34 ms and is included in actual first-stroke checks.

The real 1080p overlay checks use voice off and ordinary motion, including font, camera and drawing startup. First-stroke medians over TCP/OAuth/DNS are 2.85 seconds for DeepSeek and 4.01 seconds for Groq GPT OSS 120B. A recorded GPT OSS 20B probe did not draw and is not a qualified default. TTS startup is not tested by these latency checks. The ≥90% three-provider golden gate and half-token gate pass; the ≤3-second fast-provider latency gate does not. Keep `released = false` in `src/main/board/feature.ts`. Developers can enable phase 2 with `KITE_BOARD_PHASE2=1`; `0` retains the legacy tool. The existing Whiteboard action toggle gates both paths. The model picker appears only when phase 2 is enabled.

Validation: 272/272 unit tests passed serially, including eleven new script/planner/family/integration tests; the final targeted board suite passed 41/41. Type checking, lint, native smoke, renderer smoke and main production build passed. Native tests exercise the real Electron ELK worker, model preference persistence and old archives. Renderer checks cover the model picker and existing history/thumbnail/playback flows. Default rollout requires passing fresh actual-renderer latency checks, not substituting graph-readiness timings or choosing only favorable samples.
